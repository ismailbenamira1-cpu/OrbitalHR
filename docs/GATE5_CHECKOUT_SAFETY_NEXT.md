# Checkout safety review
Staging reservation SQL limits occupied slots to ten and serializes allocation. Reservations are deliberately not released on timeout or cancellation alone; Stripe session expiration and absence of a subscription must be confirmed before release. This can temporarily exhaust slots. Paid slots remain occupied even after cancellation. Per-login identity is not company identity; founder must approve company eligibility before production.
Webhook verifier authenticates raw bytes and rejects live events; it does not reconcile invoices or mutate billing. No endpoint exposed.
Before session creation: persist immutable attempt parameters and customer binding, use Stripe idempotency keys, recover ambiguous responses, refuse retries beyond Stripe idempotency retention, and implement verified expiry/release. Enforce explicit 12-month offer terms; no indefinite $99 recurring offer in production. Test checkout must remain disabled until isolated staging and credentials are configured.
Before webhook activation: atomic event processing and account updates, current Stripe state reconciliation with concurrency fencing, settled invoice period validation, refund/dispute policy, cancellation and replay tests. No success redirect grants access.
